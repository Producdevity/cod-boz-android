# Architecture

The app is an ARM64 host for the original ARM32 `boz.s3e` image. It does not
emulate Android and never asks Android to load the game's old native library.
Dynarmic executes the game's ARMv7 and Thumb instructions; Marmalade/S3E and
OpenGL ES calls cross into native host implementations.

## Activity model

The game uses a framework `Activity` with a `SurfaceView`. The guest runtime
owns its thread, callback queue, EGL context, and input translation, so a second
native event loop would duplicate lifecycle ownership. EGL retains the context
on a pbuffer while the Android surface is unavailable.

```text
Android app (Kotlin)
  APK import, resource preparation, profile, SurfaceView and input
                              |
                             JNI
                              |
libcodboz_runtime.so (arm64-v8a)
  runtime coordinator and callback queue
  guest memory, heap, handles, loader and relocator
  S3E imports, game fixups, EGL/GLES, audio, files and sockets
                              |
                     Dynarmic A32 JIT
                              |
              ARM32 boz.s3e guest image
```

## Guest memory and imports

The guest has its own checked 32-bit address space. Guest pointers, sizes,
handles, and callbacks are explicit `uint32_t` values; host pointers are not
stored in guest memory.

The loader maps the S3E image at its preferred base and writes stable trap
addresses into external relocation slots. A JIT no-execute fault in the trap
range returns control to the import dispatcher. The dispatcher reads AAPCS32
arguments from registers and the guest stack, calls the host implementation,
writes results back, and resumes at the guest link register.

The supported game's import list is generated by CMake from
`native/bridge/imports.json`. The runtime checks that inventory before booting.
The descriptor records the exact ordered symbol inventory and calling
convention. Handler code uses the typed AAPCS32 argument helpers directly;
signatures are not inferred from symbol names. The ABI suite covers register,
stack, pointer, 64-bit, float, double, ARM, and Thumb cases.
Guest callbacks use the same AAPCS32 soft-float rules, including 64-bit stack
alignment and integer, float, and double return values. Callback execution
preserves the interrupted guest CPU and VFP state.

Dynarmic's generated code follows W^X: code pages are writable while emitted,
then changed to read-execute before use. The Android self-test also scans the
process maps and rejects any remaining read-write-execute mapping.
The game-specific fault recovery points split JIT blocks around the exact
instructions that need a post-access halt check. Generic CPU instances retain
Dynarmic's global memory-access check; the game runtime does not pay that cost
after every guest load and store.

Extension tables use the same trap mechanism. Host events are queued and guest
callbacks are invoked only on the guest thread, with a dedicated callback return
trap.

## Platform backends

- EGL creates a real GLES 2 context and keeps it alive on a pbuffer while the
  Android surface is absent. Reattaching a surface does not restart the guest.
- GLES handlers translate guest buffers and strings before calling the device
  driver. The host reports a conservative GLES 2 capability profile to keep the
  game on its compatible renderer path.
- Android audio handles streamed music and decoded PCM sound channels. Guest
  generator callbacks are drained on the guest thread before the PCM is handed
  to Android. The guest sees Android's native mixer rate separately from the
  default and per-channel PCM rates. Completed static tracks retain a short
  output-tail grace period before release. Audio focus is released while the app
  is backgrounded and reacquired before playback resumes. Voice chat is opt-in:
  Android captures 8 kHz mono PCM only after microphone permission is granted,
  stops capture while the app is backgrounded, and keeps guest capture and render
  callbacks serialized on the guest thread.
- The virtual filesystem exposes imported assets and a separate writable save
  root. DTRZ resource archives are read without exposing host paths to the game.
- The guest display uses the closest mode the game supports: 640x480 or
  854x480. Android fits that fixed buffer inside the available display and
  leaves bars outside the content instead of cropping or stretching it. Touch
  events are translated from the fitted surface into guest coordinates and
  forwarded to the guest in FIFO order, including Android's coalesced historical
  motion samples. The queue is bounded and discards only old motion samples under
  sustained overload. Each transition remains pending
  until the guest's main loop acknowledges it with `s3ePointerUpdate`; motion
  samples between transitions are not collapsed. The guest receives the game's
  original Android touchscreen path. When a physical USB or Bluetooth controller
  is present, the guest instead sees the Xperia Play keyboard/touchpad ABI;
  the sticks use the Xperia Play touchpads, while gameplay buttons call the
  game's verified input-action publishers with their original press and release
  semantics. A, B, Start, and the D-pad are exposed as Xperia keys only while
  the guest frontend polls its menu input path. The bridge records the frontend
  manager at verified keyboard call sites and reads its active state before
  publishing gameplay actions, preventing menu navigation and menu transitions
  from activating the old Xperia gameplay bindings.
  Virtual gamepad sources are excluded; Android does not report external-device
  metadata consistently enough to reject non-virtual controllers on that basis.
- BSD sockets and asynchronous DNS are native. Demonware hostnames route to the
  configured compatible server without modifying the guest image. Android NSD
  implements the guest ZeroConf search, publication, update, and removal
  callbacks. API 34 and later track live service information through
  `ServiceInfoCallback`; earlier releases use one-shot resolution. TXT updates
  are coalesced to avoid re-registering every frame.

## Import and preparation

Import accepts only the known 1.0.11 APK. It validates the complete ZIP and
required assets in a staging directory, then atomically replaces the active
import. An invalid or interrupted replacement leaves the previous working
import untouched. Verified resource archives move into the replacement without
being copied, and immutable imported files are owner-read-only.

Supported-source metadata has one checked-in definition in
`config/source-profile.json`. CMake generates the native constants from it, and
Android packages the same file for resource preparation. The offline source
inspector combines native S3E parsing with the Android SDK's manifest and
signature tools, then checks the resulting report, including its complete
component inventory, against that profile.

The importer also extracts the game resource URL from the verified guest image.
Android accepts only the exact allowlisted Activision URL. A foreground service
downloads the two required archives to partial files, resumes with HTTP byte
ranges, checks server and final file sizes, verifies pinned SHA-256 values, and
renames each verified file into place. A resource manifest is written last. The
native runtime refuses to boot until both the import and resource manifests are
present and the archive sizes match. The downloader writes the resource
manifest only after verifying both pinned hashes. The launcher can remove only
the downloaded archives and their manifest before fetching clean copies; the
imported guest, configuration, and save data stay in place. Import verification,
resource-state checks, and runtime diagnostics do not run on the Android UI
thread.

## Game-specific compatibility

The original binary has a small set of known fixed-address faults. They are
handled as named, counted image-relative JIT fault fixups that inspect and
update guest state. Each fixup has a direct host regression test.
The configured player name is applied only after verifying the expected bytes
at the supported 1.0.11 offsets.

## Android packaging

The application targets API 36, supports API 24 and later, and ships only
`arm64-v8a`. NDK r28 produces 16 KiB-aligned native libraries. The complete
runtime has also been exercised on a 16 KiB-page Android 16 system image. CI
checks Kotlin formatting, Android lint, host C++ tests, proprietary-data
exclusion, ELF load alignment, APK ZIP alignment, ABI inventory, and debug APK
signing. A CodeQL workflow is configured for first-party Kotlin and C++ on
changes to `master`, pull requests, and a weekly schedule.

The launcher can copy or save a plain-text diagnostics report. It includes the
device and display profile, host APK hash, host ABI and page size, guest CPU
state, source hash, EGL renderer, bounded GL counters, and timestamped guest
faults. A bounded private journal retains lifecycle, resource, and game-start
events across process restarts. Android 11 and later can also provide
process-exit metadata and retained text ANR traces. Raw binary tombstones are
excluded. Reports redact configured player and server values, network
addresses, URLs, email addresses, and app-private paths.
